# Implementation Plan: Управление модулями на поле пульта

**Branch**: `003-module-control-canvas` (контекст Spec Kit; текущая Git ветка `001-instruction-library`) | **Date**: 2026-10-31 | **Spec**: [spec.md](spec.md)

**Input**: добавление модуля через отдельное окно слева, автоматическое появление соответствующего блока управления, перемещение в границах поля и закрепление галочкой.

## Summary

Перестроить временно пустой пульт в поле из независимых блоков управления модулями. «Настроить» открывает левую панель в стиле редактора блоков; «+» открывает отдельный выбор моторных модулей. После выбора блок появляется на поле и может перемещаться до подтверждения галочкой. Подтверждённая раскладка сохраняется локально и в профиле, а моторные команды доступны только в рабочем режиме после READY.

## Technical Context

**Language/Version**: TypeScript 5.7 для API/валидации, JavaScript ES modules для пульта, MicroPython/Pybricks для хаба  
**Primary Dependencies**: Next.js 15, React 19, Supabase SSR/Auth, Web Bluetooth, текущий протокол Pybricks BLE  
**Storage**: локальный ключ `tlc.controller-layout.v1` и Supabase Auth user metadata через `/api/controller-layout`  
**Testing**: проверки модели и серверного валидатора, сборка Next.js, браузерные сценарии мыши/касания/клавиатуры, аппаратная приёмка  
**Target Platform**: HTTPS браузер на компьютере и телефоне; совместимый Powered Up хаб с Pybricks  
**Project Type**: существующее веб приложение со статической страницей пульта, Next API и программой хаба  
**Performance Goals**: перемещение следует за указателем без сетевой записи на каждом кадре; остановка мотора при отпускании и при существующем таймауте хаба 600 мс  
**Constraints**: нет команд при размещении; блок в границе; уникальные порты; совместимость со старыми конфигурациями  
**Scale/Scope**: один пульт на ученика, до 12 модулей и 6 портов, максимум один привод

## Design sequence

1. Синхронно расширить клиентский и серверный валидаторы полем `moduleLayout`; определить миграцию старой конфигурации и ограничение координат. Сохранить прежний API и ключ локального хранилища.
2. Построить левую панель и отдельное окно выбора. В карточках оставить настройку портов, скорости и реверса. При добавлении создавать устройство, назначать свободные порты и его блок в одном черновике; при удалении очищать оба объекта.
3. Реализовать ограниченное перетаскивание и управление с клавиатуры. Держать временные координаты отдельно от подтверждённой конфигурации, отменять жест и закрытие без галочки.
4. После галочки рендерить неподвижные блоки. Для каждого модуля маршрутизировать кнопки по `device.id` и портам; поддержать независимые моторные блоки и замки, сохранив стоп, READY gate и таймаут хаба.
5. Проверить миграцию, сохранение, мобильное размещение, доступность и потерю связи по [quickstart.md](quickstart.md). Публиковать клиент и сервер одним релизом.

## Risks and boundaries

- Текущий `gamepad.actionDeviceId` выбирает один мотор. Для нескольких карточек потребуется маршрутизация по `device.id`; старое поле остаётся совместимым при чтении.
- На телефоне адаптация меняет видимые координаты и высоту поля без потери сохранённого порядка и без горизонтальной прокрутки.
- Программа хаба управляет моторами. Датчики не предлагаются как рабочие до расширения протокола.
- Локальная сборка не доказывает физическое направление мотора или успешное Bluetooth соединение.

## Complexity Tracking

Ратифицированных правил конституции нет. Новое поле раскладки и карта активных моторных вводов необходимы для независимого блока у каждого модуля; отдельный API и новая прошивка не требуются для поддерживаемых моторных типов.
