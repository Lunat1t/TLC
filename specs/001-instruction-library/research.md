# Research: библиотека инструкций и запуск ученической среды

## 1. Где хранить инструкции

**Decision**: Supabase Postgres хранит записи инструкций, шаги, темы, состояние публикации, выбор ученика и команды запуска. Закрытый Supabase Storage хранит обложки, изображения шагов и PDF. В базе сохраняются ключи объектов, а не адреса провайдера.

**Rationale**: TLC уже использует Supabase Auth и таблицу `profiles`. Отдельное файловое хранилище и база добавили бы вторую систему прав. Закрытый bucket защищает шаги, документы, черновики и снятые материалы. Публичны только опубликованные карточки и разрешённые обложки. Сервер проверяет активный адресованный запуск и текущий планшет перед выдачей шагов или файла. Запуск фиксирует неизменяемую версию материалов: архивация запрещает новые запуски, но не прерывает уже открытую сборку. Файлы загружаются через Storage API, а не прямым изменением `storage.objects`.

**Alternatives considered**: Файлы и JSON в Git удобны для нескольких статичных инструкций, но каждое добавление требует сборки сайта и увеличивает репозиторий бинарными файлами. Vercel Blob подходит для медиа, но база и авторизация всё равно остаются в Supabase. Публичный bucket упростил бы выдачу, но любой владеющий URL смог бы открыть файл черновика. Переносимость обеспечивают экспорт метаданных и ключей файлов.

**Sources**: [Storage buckets](https://supabase.com/docs/guides/storage/buckets/fundamentals), [Storage access control](https://supabase.com/docs/guides/storage/security/access-control), [Storage schema](https://supabase.com/docs/guides/storage/schema/design).

## 2. Что считать учеником «в системе»

**Decision**: Для каждого ученика существует не более одного активного сеанса планшета с номером поколения и последним подтверждением активности. Новый подтверждённый вход атомарно заменяет прежний сеанс. Админка показывает одну строку на ученика с действительным сроком активности. Список учеников и выборы доступны только администратору.

**Rationale**: Один лишь факт входа не означает онлайн. Supabase Auth single-session не обеспечивает немедленное выключение прежнего планшета: ограничение зависит от тарифа и применяется при обновлении токена. Поэтому сервер проверяет текущее поколение сеанса при каждом защищённом чтении и изменении. Активация нового планшета допустима только после подтверждённого нового входа; сервер сверяет идентификатор Auth-сеанса с последним сеансом этого пользователя доверенным способом. Повторный heartbeat или старый JWT не могут вернуть прежнему планшету активность. При смене планшета открытый запуск и прогресс остаются за учеником, а не за прежним устройством.

**Alternatives considered**: Supabase Presence хорошо показывает текущие соединения, но общий канал может раскрыть присутствие учеников друг другу при ошибке политики. Одного Auth single-session недостаточно для мгновенной смены устройства. Одна серверная запись с ограниченным сроком активности и поколением проще для первого класса; при росте можно заменить способ уведомлений, сохранив правило одного активного планшета.

**Sources**: [Auth sessions](https://supabase.com/docs/guides/auth/sessions), [Sign out](https://supabase.com/docs/guides/auth/signout), [Presence](https://supabase.com/docs/guides/realtime/presence), [Realtime authorization](https://supabase.com/docs/guides/realtime/authorization), [Postgres Changes](https://supabase.com/docs/guides/realtime/subscribing-to-database-changes).

## 3. Как запускать среду сборки на планшете

**Decision**: После выбора учеником опубликованной инструкции сервер атомарно создаёт адресованный ученику запуск по команде администратора и фиксирует снимок материалов. Подписка сообщает активному планшету о записи; при входе, переподключении, смене планшета и возврате вкладки он запрашивает ожидающий или открытый запуск вместе с сохранённым шагом. Старый планшет теряет право на защищённые действия. Новый выбор во время сборки атомарно сохраняет прогресс, закрывает прежний запуск и переходит в ожидание следующей команды. Повторный запрос с тем же ключом идемпотентности не создаёт второй запуск.

**Rationale**: Только событие WebSocket пропадёт при обрыве связи, а запись в базе сохраняет команду и состояние для админки. Для первого класса небольшого размера Postgres Changes достаточно; при росте можно перейти на Broadcast, оставив запись источником истины. Supabase рекомендует Broadcast для масштабируемости и безопасности, а Postgres Changes как более простой путь на малой нагрузке.

**Alternatives considered**: Чистый Broadcast без записи не переживает офлайн/обрыв. Периодический опрос без подписки проще, но замедляет запуск и увеличивает запросы. Автоматический переход без проверки несохранённой работы может уничтожить работу ученика.

**Sources**: [Subscribing to database changes](https://supabase.com/docs/guides/realtime/subscribing-to-database-changes), [Realtime authorization](https://supabase.com/docs/guides/realtime/authorization).

## 4. Как выдавать закрытые шаги после архивации

**Decision**: Публичные запросы получают только карточку опубликованной инструкции. Шаги и документы выдаются через проверенный маршрут по идентификатору активного запуска; сервер проверяет ученика, текущее поколение планшета и принадлежность файла сохранённому снимку. Обложка опубликованной карточки может выдаваться отдельно. Защищённые ответы не кэшируются публично. Файлы сохранённого снимка не удаляются, пока есть открытая сборка, даже если инструкция архивирована.

**Rationale**: Это одновременно скрывает шаги до команды преподавателя, прекращает доступ к ним на старом планшете и сохраняет продолжение работы после архивации или смены устройства. Уже загруженные байты нельзя удалить из памяти устройства задним числом; проверка останавливает последующие запросы и изменения.

**Alternatives considered**: Публичный bucket и прямые ссылки раскрывают документ до запуска. Подписанные URL продолжают работать до истечения срока, поэтому не дают немедленного прекращения новых запросов. Удаление файла при архивации ломает уже открытую сборку.

**Sources**: [Storage buckets](https://supabase.com/docs/guides/storage/buckets/fundamentals), [Storage access control](https://supabase.com/docs/guides/storage/security/access-control), [RLS](https://supabase.com/docs/guides/database/postgres/row-level-security), [Private file caching caveat](https://supabase.com/kb/troubleshooting/storage-private-bucket-files-still-accessible-after-remove-access-or-logout).

## 5. Доступ администратора и права на контент

**Decision**: Администратор входит через Supabase Auth; доверенная роль задаётся отдельной закрытой записью, выдаваемой владельцем системы. Роль не берётся из localStorage, никнейма или редактируемых учеником полей профиля. Права проверяются на сервере и через RLS. Публикация требует подтверждения права на каждый материал; сайт-пример служит только ориентиром пользовательского сценария.

**Rationale**: В текущем checkout кнопка входа учителя отключена, а рабочий маршрут админки отсутствует. Таблица `profiles` сейчас допускает публичное чтение и обновление собственного профиля, поэтому добавлять в неё саморедактируемый флаг администратора опасно. Необходимо ограничить доступ к списку учеников отдельной политикой/серверным маршрутом. Авторские файлы примера нельзя автоматически считать доступными для копирования.

**Alternatives considered**: Флаг администратора в браузере или редактируемом профиле не является доверенной авторизацией. Общий пароль админки не даёт надёжной идентичности и аудита. Прямой импорт стороннего каталога не включён без прав и исходных материалов.

**Sources**: [Row Level Security](https://supabase.com/docs/guides/database/postgres/row-level-security), [пример каталога EV3](https://legoowedoo.tilda.ws/instruction-lego-ev3).

## Open implementation checks

- До реализации проверить доступный тариф Supabase и лимиты файлов/трафика; план не предполагает платных функций обработки изображений.
- Уточнить, есть ли отдельный ещё не включённый админский код: в текущей ветке его не обнаружено. План предусматривает создание входа и раздела админки в этом репозитории.
- Первые инструкции и права на их публикацию предоставляет владелец TLC; до получения материалов можно проверить сценарий на собственных тестовых изображениях.
